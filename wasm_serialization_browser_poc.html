code_size → JIT Write

ReadCode() ~L1023 · CopyAndRelocate() ~L1082

DCHECK_GE(remaining_code_size_, code_size) stripped in release. ReadVector reads past blob end; CopyCode copies those bytes into RWX JIT memory.

ReadVector no upper-bound CHECK

Reader::ReadVector() ~L112 · NativeModuleDeserializer::ReadCode() ~L1038

pos_ advances code_size bytes with no release-build bounds guard. Returns a vector whose .begin() is past the blob buffer end.

CWE-129 · Invalid Array Index · HIGH

External ref tag OOB

address_from_tag(tag) ~L1140

tag from blob reloc section. Only DCHECK_GT — stripped in release. Indexes into ExternalReferenceTable past its length.

CWE-129 · Invalid Array Index · HIGH

Wild jump-table target

GetNearCallTargetForFunction(tag) ~L1102

Function index unchecked in release. Writes arbitrary call-target into Wasm jump table. Attacker controls which address is installed as next hop.

CWE-125 · OOB Read · HIGH

code_pointer_handles OOB

GetCodePointerHandle(index) ~L1128

No upper-bound CHECK on code pointer handle index from blob. Reads from code pointer table with attacker-controlled offset.

CWE-125 · OOB Read · HIGH

canonical_sig_id OOB

canonical_type_id(module_local_sig_id) ~L1122

V8_ASSUME (not CHECK) on sig id range. In release builds V8_ASSUME is a compiler hint, not a runtime guard. OOB read of canonical type table.

CWE-125 · OOB Read · HIGH

LEB parse OOB — effect-handler table

LEBHelper::read_u32v → ~L348

Effect-handler table parsing uses read_u32v with no end-of-buffer parameter. Malformed high-bit-set LEB bytes walk pos_ past blob end indefinitely.

Live PoC — Pure JavaScript, No Native Syntax

The buttons below run pure JS (standard WebAssembly.* APIs, no --allow-natives-syntax). Steps 1–3 work in any browser. Step 4 (actual deserialization of crafted bytes) requires d8_poc: ./out/x64.release/d8_poc --no-liftoff wasm_serialization_poc.js — confirmed to trigger OOB read/write on this V8 build. In Chrome, the equivalent path is the HTTP code cache (see attack path below).

Chrome Attack Path — HTTP Code Cache (No Hash Check)

Renderer Sandbox → V8 Deserialization

Chrome caches compiled Wasm modules in its HTTP disk cache as "side data". The deserialization path has no equivalent to d8's hash check. Any party that can write crafted bytes to the code cache entry triggers these findings.

Attacker injects crafted bytes into Chrome HTTP cache → URLRequestJob fetches cached entry →
CodeCacheHost::ReceiveCachedCode → WasmCodeSerializer / WasmCodeDeserializer →
NativeModuleDeserializer::Read() → ReadCode() → ReadVector(code_size) → CopyAndRelocate() →
OOB read of heap memory + OOB write into RWX JIT code space → Arbitrary code execution in renderer

Cache injection vectors: HTTP MITM (plain HTTP sites), server-side cache poisoning, compromised CDN, network process exploit, Chrome extension with webRequest permissions. Cache path: %LOCALAPPDATA%\Google\Chrome\User Data\Default\Cache\Cache_Data\ (Windows), ~/.config/google-chrome/Default/Cache/ (Linux).
