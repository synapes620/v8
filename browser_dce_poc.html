V8 ExternConvertAny DCE — Incorrect Effects Declaration

Authorized security research · Turboshaft DCE via ExternConvertAnyOp.effects = CanDependOnChecks()

Bug Summary

CVE candidate — CWE-670 (incorrect effects)
File: src/compiler/turboshaft/operations.h:7999
Struct: ExternConvertAnyOp
Declared effects: OpEffects().CanDependOnChecks() — no allocation, no heap writes
Actual effects: May allocate JS wrapper + write js_wrapper_ field for WasmCustomMap inputs

When the result of extern.convert_any is dropped (unused), Turboshaft DCE eliminates the op in the first optimization pass (LoopPeeling). The runtime call WasmExternConvertAny is never generated, so no allocation occurs. This is "safe" for plain JS objects but skips eager wrapper creation for Wasm structs.

Related Finding

Latent — DCE line 266 CallOp bypass
File: src/compiler/turboshaft/dead-code-elimination-reducer.h:266
is<CallOp>() arm intercepts before IsRequiredWhenUnused() for ALL CallOps. Currently unexploitable: the vulnerable CallRuntime<WasmExternConvertAny> path in wasm-lowering-reducer.h:308 is unreachable because WasmLoweringPhase only runs in the kWasm pipeline where the protected kWasm branch is taken.

Root Cause

// operations.h:7993-8010
struct ExternConvertAnyOp : FixedArityOperationT<1, ExternConvertAnyOp> {
  bool is_nullable;
  // ↓ INCORRECT: missing CanAllocate() + CanWriteHeapMemory()
  static constexpr OpEffects effects = OpEffects().CanDependOnChecks();
  //              ↑ required_when_unused = false
  //              ↑ allocation_requirement = none
  //              ↑ heap_write_requirement = none
};

// What WasmToJSObject actually does (runtime-wasm.cc → wasm-objects.cc):
// For WasmCustomMap inputs:
//   if (js_wrapper_ == null) CreateJSWrapper(isolate, map);  ← allocates
//   else return cached js_wrapper_;
// → Should declare: OpEffects().CanAllocate().CanWriteHeapMemory()

// In DCE (dead-code-elimination-reducer.h:ProcessBlock):
//   if (op.Is<CallOp>()) { ... }         ← line 266: CallOp bypass
//   else if (op.IsRequiredWhenUnused()) { ← not reached for CallOp
//     op_state = kLive;
//   }
//   // For ExternConvertAnyOp (NOT a CallOp):
//   //   IsRequiredWhenUnused() → effects.is_required_when_unused() = false
//   //   → op_state stays kDead → op eliminated

Impact

Severity: Incorrect effects declaration (wrong metadata for optimization passes)

Impact 1 — DCE correctness (observable, low severity)
  extern.convert_any + drop skips JS wrapper allocation for WasmCustomMap objects.
  V8 uses lazy initialization (js_wrapper_ populated on demand), so the eager
  allocation skipped by DCE is recreated on the next access. No crash in V8 as-is.

Impact 2 — Load elimination (theoretical, medium severity)
  Other optimization passes (load elimination) read OpEffects to reason about memory.
  ExternConvertAnyOp declaring "no heap writes" can mislead load elimination:
  if LI caches a load of js_wrapper_ from before the extern.convert_any op, it may
  incorrectly serve the cached (null) value after the op, since it believes the op
  wrote nothing. This breaks the invariant that js_wrapper_ is populated after the op.
  Triggering this requires the right JIT code shape with WasmCustomMap inputs.

Impact 3 — DCE line 266 bypass (latent)
  is<CallOp>() arm intercepts before IsRequiredWhenUnused() for ALL CallOps.
  When a future refactor causes WasmLoweringPhase to run in a non-kWasm context
  (e.g. during JS-to-Wasm inlining improvements), the vulnerable else-branch in
  wasm-lowering-reducer.h:308 becomes reachable, and the narrow kEffects on
  WasmExternConvertAny combined with the DCE bypass allows full call elimination.
