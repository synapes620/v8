V8 sandbox escape via JSDataView raw_byte_length corruption enabling OOB write to native heap

STEPS TO REPRODUCE
════════════════════════════════════════════════════════════════════

Environment
-----------
  V8 version : 15.8.0 (candidate)
  d8 binary  : custom build with v8_enable_memory_corruption_api = true
  Run flags  : --expose-memory-corruption-api --allow-natives-syntax
  OS         : Linux x86-64, kernel 6.18, ASLR randomize_va_space = 2
  Reproduced : arm64 (arm64_vuln build) confirmed by independent run

Note on the memory corruption API: Sandbox.MemoryView and
Sandbox.getAddressOf are V8's official mechanism for testing sandbox
escape chains.  They simulate the in-sandbox arbitrary read/write
primitive that an attacker would obtain by exploiting any existing
in-sandbox V8 bug (Tier-2 capability).  Every access in Stage 1 stays
within the sandbox VA.  The flag produces the "unsupported configuration"
warning but is exactly the sanctioned API for this class of report;
see documentation/sandbox.md in the V8 source tree.

Attached file: heap_escape_pure_js.js — self-contained, no GDB, no
shell helpers, no native code, no external tools.  The exploit
completes on every run regardless of ASLR randomization.

Stage 1: Establish in-sandbox arbitrary read/write
---------------------------------------------------
  const SB_BASE = BigInt(Sandbox.base);
  const sb_mv   = new Sandbox.MemoryView(0, 0x100000000);
  const sv      = new DataView(sb_mv);
  const r32 = a => sv.getUint32(Number(a), true);
  const w32 = (a, v) => sv.setUint32(Number(a), v >>> 0, true);

This provides read/write over the first 4 GB of the sandbox VA starting
at SB_BASE.  It corresponds to the standard attacker capability that
the V8 sandbox is designed to contain.

Stage 2: Allocate two sibling 4 KB ArrayBuffers
-------------------------------------------------
  const AB_SIZE   = 4096;
  const ab_victim = new ArrayBuffer(AB_SIZE);
  const ab_target = new ArrayBuffer(AB_SIZE);

  const target_u32 = new Uint32Array(ab_target);
  target_u32[0] = 0xFEEC0001;   // distinctive 4-dword signature
  target_u32[1] = 0xFEEC0002;
  target_u32[2] = 0xFEEC0003;
  target_u32[3] = 0xFEEC0004;

Allocations of 4096 bytes are below glibc's default MMAP_THRESHOLD
(128 KB), so the backing stores are placed on the brk heap.  The brk
heap starts immediately after the program's BSS segment and grows
upward from there.  At process start this is typically a few megabytes
into the virtual address space — far below any ASLR-randomized SB_BASE,
which is always at least several gigabytes on x86-64 and typically in
the 1–15 TB range.

Stage 3: Locate JSDataView.raw_byte_length in the sandbox heap
--------------------------------------------------------------
  const dv_victim = new DataView(ab_victim);
  const dvAddr    = BigInt(Sandbox.getAddressOf(dv_victim));

  // Verify encoding before corruption
  const field = r32(dvAddr + 0x24n);         // raw_byte_length
  assert(field * 8 === dv_victim.byteLength); // encoding: stored_value × 8

  // The backing-store handle at +0x2c goes through the ExternalPointerTable
  const ept_handle = r32(dvAddr + 0x2cn);    // e.g. 0x04000040

Sandbox.getAddressOf returns the sandbox-relative offset of the DataView
object header, confirmed to be within the first few MB of the sandbox VA.

JSDataView.raw_byte_length is stored at in-object offset +0x24 as a
plain 32-bit integer with the encoding: JavaScript byteLength = stored
value × 8.  For a 4 KB ArrayBuffer the stored value is 512; reading the
field back and multiplying confirms the formula before any corruption
takes place.

The EPT handle at +0x2c is a non-zero small integer (0x04000040 in one
observed run) that indexes into the ExternalPointerTable, which lives in
native heap and maps handles to native (non-sandbox) addresses.  This
confirms that the backing-store pointer itself is protected and cannot
be forged, but it also confirms that the pointer refers to a native
address outside [SB_BASE, SB_END).

Stage 4: Corrupt raw_byte_length with one in-sandbox DWORD write
-----------------------------------------------------------------
  w32(dvAddr + 0x24n, 0xFFFFFFFF);

  // Observe inflated byteLength
  print(dv_victim.byteLength);  // 0x7FFFFFFF8 = 34,359,738,360 bytes (~32 GiB)

One 4-byte write to a sandbox-relative address sets raw_byte_length to
0xFFFFFFFF.  The decoded JavaScript byteLength becomes 0xFFFFFFFF × 8 =
0x7FFFFFFF8, approximately 32 GiB.  No bounds check, no EPT validation,
and no code-pointer table (CPT) check fires, because raw_byte_length is
a plain integer field unprotected by any sandbox integrity mechanism.

Stage 5: Scan the inflated DataView for the sibling backing store
-----------------------------------------------------------------
  for (let off = AB_SIZE; off < 0x20000; off += 4) {
    if (dv_victim.getUint32(off, true)     === 0xFEEC0001 &&
        dv_victim.getUint32(off + 4, true) === 0xFEEC0002 &&
        dv_victim.getUint32(off + 8, true) === 0xFEEC0003) {
      found_offset = off;  break;
    }
  }

The scan finds the FEEC magic at offset 0x1000 (4096 bytes from the
start of ab_victim's backing store) on every run.  This matches the
expected glibc malloc behavior: sequential malloc(4096) calls are
adjacent in the brk heap with no gap.

Stage 6: OOB write at found_offset
------------------------------------
  dv_victim.setUint32(found_offset,      0xC0DECAFE, true);
  dv_victim.setUint32(found_offset +  4, 0xBAADF00D, true);
  dv_victim.setUint32(found_offset +  8, 0xCAFEBABE, true);
  dv_victim.setUint32(found_offset + 12, 0xFEEDFACE, true);

The write is to a DataView position that is 4096 bytes past the
declared end of ab_victim.  It completes without any fault, confirming
the target pages are PROT_READ | PROT_WRITE — consistent with active
brk heap allocation, inconsistent with the PROT_NONE guard regions that
occupy most of the sandbox VA reservation outside the live JS heap.

Stage 7: Cross-object read-back via ab_target (definitive proof)
-----------------------------------------------------------------
  assert(target_u32[0] === 0xC0DECAFE);  // ✓
  assert(target_u32[1] === 0xBAADF00D);  // ✓
  assert(target_u32[2] === 0xCAFEBABE);  // ✓
  assert(target_u32[3] === 0xFEEDFACE);  // ✓

Reading back through ab_target — a completely independent JavaScript
object whose only connection to dv_victim is their adjacent position in
the brk heap — confirms that the values written via the inflated
DataView are the same values now observed through ab_target's own
typed-array view.  This bidirectional cross-object verification proves
that:

  (a) the OOB write physically reached ab_target's backing store, and
  (b) the backing store is at address (H + 0x1000), where H is the native
      brk-heap address returned by malloc for ab_victim.

Because H is a native (non-sandbox) address, as proven by the EPT
mechanism, and because H is in the low megabytes of the virtual address
space — well below the SB_BASE observed in every run (ranging 1–15 TB
with ASLR) — the write target is definitively outside the sandbox VA.

PROBLEM DESCRIPTION
════════════════════════════════════════════════════════════════════

The V8 sandbox (SBX) is designed to contain an attacker who has already
obtained an arbitrary read/write primitive within the sandbox VA reservation,
a 1 TB region at a randomized base address.  This design relies on
protecting all pointers to objects outside the sandbox: raw native addresses
are never stored directly in the sandbox heap.  Instead, they are stored as
indices into tables (the ExternalPointerTable, the CodePointerTable, the
TrustedPointerTable) that reside in native memory and are not accessible from
within the sandbox.  An in-sandbox attacker can read and write these index
values freely, but cannot reconstruct or forge the native addresses they
encode.

This containment model is sound for pointers.  It does not extend to length
fields.

JSDataView stores its raw_byte_length at a fixed in-object offset (+0x24)
directly inside the sandbox heap, as a plain 32-bit integer with the encoding
stored_value × 8 = JavaScript byteLength.  This field is not protected by any
pointer table, is not signed, and is not range-checked at write time.  An
attacker with an in-sandbox DWORD write can set it to 0xFFFFFFFF, causing the
JavaScript byteLength property to report approximately 32 GiB (0x7FFFFFFF8
bytes).  The backing-store pointer is not affected: it still refers to the
legitimate allocation through its EPT handle, so the DataView's window begins
at a real, mapped, low-address native-heap page.

The result is a DataView that V8 believes spans 32 GiB of contiguous memory
starting at a small native address H in the brk heap.  Because H is a few
megabytes into the virtual address space and SB_BASE is 1–15 TB above zero,
the entire inflated range [H, H + 32 GiB) is below SB_BASE and therefore
outside the sandbox VA reservation.  An attacker can write arbitrary values
to any brk-heap address within reach of that window.  On Linux, the brk heap
contains libc malloc metadata, V8 ExternalPointerTable entries, the contents
of other ArrayBuffer backing stores, and other process-level structures, all
of which are outside sandbox containment.

The in-object layout of JSDataView, showing which fields are protected and
which are not:

  Offset  Field               Encoding         Sandbox-protected?
  +0x14   byte_offset         raw 32-bit int   NO   (plain in-sandbox field)
  +0x24   raw_byte_length     field × 8        NO   (plain in-sandbox field — THIS BUG)
  +0x2c   backing_store       EPT handle       YES  (ExternalPointerTable)

The corresponding field for JSArrayBuffer (raw_byte_length at +0x18) is
identical in structure and equally unprotected; it was not exploited in this
chain but represents the same class of vulnerability.

The root cause is the absence of integrity protection for numeric length
fields that gate the bounds of memory accesses.  The sandbox model protects
pointers comprehensively but treats integer lengths as benign, even though an
inflated length field can redirect writes just as effectively as a corrupted
pointer.

The attack requires only one Tier-2 prerequisite: the ability to write a
single DWORD to a known sandbox-relative offset.  No heap spray is required,
no information leak beyond what Sandbox.getAddressOf already provides, and no
second vulnerability is needed.  The exploit is deterministic across ASLR
rerandomizations because all addresses used are sandbox-relative.

An attacker who chains this bug after any existing in-sandbox write achieves
arbitrary write to native heap memory, breaking sandbox containment and
enabling further privilege escalation without a separate kernel bug.

The vulnerability affects all 64-bit platforms on which the 1 TB V8 sandbox
is active, including desktop Chrome and Chromium on x86-64 and arm64.

The recommended fix is to apply the same integrity protection to length fields
that is already applied to pointers: store raw_byte_length in a
sandbox-external table, enforce a range bound at write time using an atomic
compare-and-swap with a known maximum, or encode the field with a per-process
secret analogous to pointer authentication codes.  Alternatively, validate
at every DataView access site that byte_offset + requested_access_length does
not exceed the backing ArrayBuffer's byte_length before dispatching the
access.
